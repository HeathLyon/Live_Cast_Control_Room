# Set up the new paid server and GitHub Pages

## 0. Before purchase

This package is independent of your working v0.5 demo. **Do not overwrite the demo repository/service.** Create a fresh repository (recommended name `Live_Cast_Control_Room`). Using a separate production database keeps testing from altering actual results.

Estimated base cost as of November 2026: Render Starter web service **$7/month** plus 5 GB disk at **$0.25/GB/month = $1.25**, or about **$8.25/month** before other usage, fees and taxes. The included paid Blueprint uses **one worker**, not a managed PostgreSQL database. The existing SQLite code cannot use Postgres without a separate migration.

## 1. Upload the complete project to GitHub

1. Download and unzip `Live_Cast_Control_Room_Unified_v2_Full.zip`.
2. In GitHub, create a new repository called `Live_Cast_Control_Room`. Do not upload the ZIP as one file; upload its **contents** at the repository root. Use Codex to review/import if easier.
3. Make `main` your deployment branch. Verify `app.py`, `render.yaml`, `pages-overlay.html`, `js/overlay.js`, and `js/site-config.js` are all at the root/subpaths shown in the README.
4. **Do not upload** any `.env` credentials, SQLite database, paid API keys, login hashes, or local scratch files.
5. On GitHub: **Settings → Pages → Build and deployment → Deploy from a branch → main → /(root) → Save**. Wait for Pages to publish.
6. Check the generated Pages URL. For the recommended repository name, it should be `https://heathlyon.github.io/Live_Cast_Control_Room/`.

## 2. Create a new paid Render service

1. Open <https://dashboard.render.com>, connect GitHub if needed, then **New → Blueprint**.
2. Select your **new** repository on `main`, with **Blueprint path** `render.yaml`.
3. Check that the Blueprint creates `live-cast-scoreboard-production`, with **plan `0.5c-512mb`** (Starter), and **5 GB disk mounted at `/var/data`**.
4. If the Blueprint asks for `LIVECAST_USERS_JSON`, supply a named account JSON string (see next section). The `VIEW_TOKEN` is generated by Render via `generateValue` and must remain private.
5. Deploy. Render injects `RENDER_EXTERNAL_URL` and `PORT` automatically. Set `LIVECAST_PUBLIC_URL` only if you want to override the default with a verified custom HTTPS origin.
6. Wait for `/health` to return JSON with `ok:true`, `version:2.0.0-rc1`, `mode:production`, `storage:persistent-single-node-sqlite`.
7. Open the new service root `/` (HTTP Basic prompt). Login with the named username/password set in the next section.

**Do not upgrade the existing Free demo in place.** Render disk-backed services briefly stop during redeploys, so disable auto-deployment and avoid show-time code releases.

### Redeploy an existing production service

1. On Render, open the existing service and confirm it is the intended production service. Check the linked repository, branch `main`, service root at the repository root, Starter plan, and its existing 5 GB disk at `/var/data`. Download a consistent SQLite backup from the admin console if the service already contains records.
2. Before merging, check that service auto-deploy is off. On a Blueprint-managed service, also set **Auto Sync** to **No** in the Blueprint settings to keep the merge from triggering a sync during the show.
3. In **Environment**, enter the required secrets before syncing or deploying. Existing Blueprint syncs skip `sync: false` entries. Review any existing `LIVECAST_PUBLIC_URL` override because Render retains variables omitted from a Blueprint. Remove a stale override so the service uses `RENDER_EXTERNAL_URL`.
4. Merge the reviewed PR during the maintenance window and use **Manual Sync** on the existing Blueprint. Confirm the sync targets only the intended service. For a manually configured service, apply the build command, start command, health-check path and environment settings from `render.yaml` in the existing service. If the settings update has yet to start the target deploy, use **Manual Deploy → Deploy a specific commit** and select the reviewed merge commit. Watch both build and startup logs.
5. Check `/health`, sign in with a named admin account, and verify the expected database contents and the public overlay in vMix. If `/health` returns HTTP 503, inspect the disk and SQLite path before accepting donations. Rehearse a second deploy outside the show and verify the same records remain.

### Render environment settings

| Source | Variables |
| --- | --- |
| Production Blueprint | `LIVECAST_ENV=production`, `LIVECAST_REMOTE_TEST=1`, `LIVECAST_DB=/var/data/livecast.sqlite3`, `LIVECAST_PERSISTENT_ROOT=/var/data`, `LIVECAST_REQUIRE_MOUNT=1`, `LIVECAST_SERVER_QUEUE=1`, `LIVECAST_SEED_CAST=0`, `LIVECAST_ALERT_SECONDS=6`, `PYTHON_VERSION=3.11.11` |
| GitHub Pages overlay settings | `PUBLIC_OVERLAYS=1`, `PAGES_ORIGIN=https://heathlyon.github.io`, `LIVECAST_PAGES_URL=https://heathlyon.github.io/Live_Cast_Control_Room/` |
| Required secret | `LIVECAST_USERS_JSON` with valid generated hashes and at least one admin. Set it in Render Environment. |
| Required generated secret | `VIEW_TOKEN` is generated on Blueprint creation if absent. For a manual service, generate privately with `python -c "import secrets; print(secrets.token_urlsafe(32))"` and store it in Render Environment. |
| Built in | `PORT` and `RENDER_EXTERNAL_URL` are supplied by Render. `LIVECAST_PUBLIC_URL` is an optional HTTPS override. |
| YouTube | Secret `YOUTUBE_API_KEY` is required to ingest real YouTube events. Set it manually before rehearsal. Optional settings are `YOUTUBE_ENABLED`, `YOUTUBE_VIDEO_ID`, and `YOUTUBE_MIN_POLL_SECONDS` (default 50). |

Use `OPERATOR_PASSWORD` only for staging. Production Uvicorn access logging is disabled because legacy private links accept a viewer token in the query string.

For a failed deploy, collect the deploy ID, commit SHA, Blueprint sync errors, build log from Python version selection through pip completion, and runtime log from the start command through the first traceback or health failure. Redact credentials and private link query strings before sharing.

## 3. Create private staff accounts

1. Run `python scripts/create_user_hash.py` on your own computer. Enter a unique password at the prompt. **Keep passwords out of ChatGPT, GitHub and project documentation.**
2. Repeat for each person; place the resulting hashes in a JSON mapping. In Render → your production service → **Environment**, set `LIVECAST_USERS_JSON` to an object like:

```json
{
  "director": {"role": "admin", "password_hash": "scrypt$16384$8$1$..."},
  "producer1": {"role": "producer", "password_hash": "scrypt$16384$8$1$..."},
  "reviewer1": {"role": "viewer", "password_hash": "scrypt$16384$8$1$..."}
}
```

3. Use the exact script output. Production startup rejects missing or malformed account configurations before opening SQLite.
4. Admin: backups, debug, billing-irrelevant operational controls. Producer: ledger corrections, missed-payment verification, battles, goals, graphics. Viewer: read-only operator access.
5. Current login uses HTTP Basic over HTTPS; provide MFA or a protected identity-aware proxy and rate limits before high-stakes production.

## 4. Link the GitHub Pages overlays to the new paid hostname

1. Edit **`js/site-config.js`** in the new GitHub repository and change only `backendUrl` to your real Render HTTPS origin. It contains **no token or password**.
2. Check `LIVECAST_PAGES_URL` in Render Environment matches the actual GitHub Pages base URL. The Blueprint defaults to `https://heathlyon.github.io/Live_Cast_Control_Room/`; change it if you chose another repository name.
3. Open `<your Pages URL>/pages-setup.html`. Verify the backend hostname shown. Generate and copy the vMix URLs.
4. Recommended initial vMix Web Browser inputs, each at 1920×1080: `graphic=top3-alert`, `graphic=goals`, `graphic=battle`. Keep the separate inputs in vMix overlay channels and enable only the desired graphics.
5. If the graphics look empty, check the goal/battle on-air switches, queue pause state, and public API status. The donation alert intentionally disappears between transactions. The permanent `graphic=top3` is useful as a connection test.

GitHub Pages hosts **transparent artwork only**. Render supplies public read-only score/configuration endpoints and the private operator UI. Never put a `VIEW_TOKEN` in a Pages URL.

## 5. Connect YouTube after channel access is granted

1. In Google Cloud Console, enable **YouTube Data API v3** for your project and create an appropriately restricted API key.
2. In Render → Environment, set secret `YOUTUBE_API_KEY` and deploy.
3. Open private Control Room → **YouTube live**, paste the livestream URL or 11-character video ID, enable listening.
4. Observe `listening`, the last check, chat message count, and error status. Send a **regular text chat**; it is connectivity-only and must NOT add score. For the true paid-data test, send one authorized small **Super Chat** from a monetization-eligible public live broadcast.
5. Review the original YouTube event ID, amount, currency, cast matching, duplicate behavior, timestamps, score and on-air alert. See [YouTube test plan](YOUTUBE_TEST.md).

This release's collector **still polls** the YouTube API. Test latency and move to `streamList` before committing to seconds-sensitive head-to-head battles.

The collector resumes from its saved chat checkpoint when YouTube accepts it. After an outage or restart, verify the ledger against YouTube and use the audited missed-payment workflow for any gaps.

## 6. Production protections and acceptance

- **Backups:** the attached disk persists between restarts but is not an off-server backup. Use the admin's System & Links → `Download database backup` to export a consistent snapshot, store it off-server, and rehearse a restoration. Arrange automated off-site backup before December 6.
- **Daily checks:** verify YouTube listening, the storage integrity status, actual donation counts, pending review count, alert backlog and producer access.
- **Restart rehearsal:** turn off the server during a TEST (not on-air) and ensure battles, credits, cast, goals, graphics and audit history survive.
- **Currency:** automatic ranking awards USD only. Agree on an FX policy before accepting other currencies.
- **Producer authorization:** every missing donation and score change must contain evidence and an audit reason.
- **Go/no-go:** do not use as official source of truth until the checklist in `GO_LIVE_CHECKLIST.md` is signed off.
